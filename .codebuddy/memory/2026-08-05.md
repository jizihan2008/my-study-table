## CodeBuddy CLI 能力调研（AI 编程澄清功能决策依据）
本机已装 `@tencent-ai/codebuddy-code`（`%APPDATA%\npm\node_modules\@tencent-ai\codebuddy-code`），入口 `bin\codebuddy`。**结论：CLI 自带提问能力但 `-p` 非交互模式不可用，ask/craft 不是 CLI 概念**：
- **提问能力**：CLI 有 `AskUserQuestion` 工具（模型可主动弹问题卡）、`ExitPlanMode`（plan 完成请求批准），但**仅服务于交互式终端 / ACP 协议客户端**（`--acp`，stdin/stdout ndJsonStream 双向通信）。官方文档明确：**`-p` 模式下 CLI 不会交互式追问**，一次性执行并退出；CHANGELOG 记录 print 模式提问类工具走 "ask→deny" 语义（无审批 UI 入口，自动拒绝）。
- **ask/craft/plan**：CLI **没有** `--mode ask/craft/plan` 参数。plan 是**权限模式** `--permission-mode plan`（只读分析出方案，Shift+Tab/Alt+M 切换）；ask 不是权限模式；craft 不存在。ask/craft 是 CodeBuddy IDE 对话框 UI 层概念，我们目前用 `--allowedTools`（ask/plan→'Read'）+ prompt 注入模拟，方向正确。
- **多轮/继续**：`-c/--continue` 恢复最近会话、`-r/--resume` 按 id 恢复、`--input-format stream-json` 支持 stdin 流式输入、`--replay-user-messages` 重放消息。理论上可用于多轮，但 AskUserQuestion 在 -p 下仍被 deny。
- **实现「AI 反问确认方向」的可行路线**：(A) prompt 层注入澄清约定 `{"type":"clarify","questions":[...]}` + 渲染层提问卡 + 回答后带上下文重跑（不动 CLI 协议，推荐）；(B) 改用 `--acp` 双向协议监听 AskUserQuestion 事件（最接近 CodeBuddy 原生体验，但需重写 main.js 通信层，改动大）。

### 数据层 `js/taskline.js`（新，localStorage key `study_taskline_v1`）
- 存储结构：`{version, xp, lines:[], quests:[], badges:[], rewards:[], toggle:{autoComplete}}`
- 章节 line：`{id,name,type:'main'|'quality',desc,sort,createdAt}`；任务 quest：`{id,lineId,title,status,desc:{goal,meaning,output},deps:[questId],conditions:[],rewards:{xp},milestone,sort,createdAt,completedAt}`
- 状态机：draft（AI 生成待确认）→ locked（deps 未满足）/ active → done / skipped。`tlActivateQuest` 确认草稿（deps 未满足转 locked）；`tlCompleteQuest`/`tlSkipQuest` 手动；`tlRefreshAll()` 全局刷新（主线章节锁定 + deps 解锁 + 有条件的 active 任务条件全满足自动完成 + 结算 xp 并塞 `_feedback` 即时反馈队列）
- **主线解锁**：`tlMainLineUnlocked`——主线章节前一章（sort 更小）全部任务 done/skipped 才解锁；空章节直接解锁；`tlLineProgress` 进度 = done+skipped 占比
- 完成条件 cond：`{type:'todo'|'note'|'timer'|'manual', todoId/noteId/targetId+targetType+minutes, label, done}`；`tlCheckCondition` 自动检测（todo→findTodo().done；note→notes 里 content 非空；timer→study_timer_records 按 targetId 累计 totalMs≥minutes*60000；manual→done）；`tlIsCondMet = cond.done===true || 自动检测`（自动检测类也允许手动覆盖）
- 奖励：经验每 100 升 1 级（`tlLevelFromXp`）；`tlCheckAutoBadges` 自动徽章（初试/5/10/20任务/3级/5级/章节达成）；奖励池 `tlAddReward/tlRedeemReward/tlDeleteReward`（xp 兑换）
- **关键设计坑**：自动完成只针对「有条件」的 active 任务；无条件任务激活后保持 active，需手动点完成（否则激活即完成，丢仪式感）
- `buildAiSummary()` 生成任务线状态文本（等级/主线当前章/素质线等级/激活任务/草稿/卡点），供 AI system prompt 注入
- 待办联动：`tlOnTodosChanged()` 在 todos.js `toggleTodo`、ai-tools.js `toggle_todo`/`batch_update_todos(toggle_completed)` 保存后调用（自动结算 + 弹通知）

## 任务线 DAG 多线改造 v0.2.6（2026-08-05，多线交织 + 跨章节依赖可见）
用户指出「GTNH 不是单线任务，是每个章节一张 DAG 图，章节间任务也能互相依赖」，核心痛点是「AI 老把任务排成单一直线链」。两轮澄清确认：**每章节独立 DAG 图**（不做全局合并）、保留章节概念、**允许跨线依赖**、保留主线顺序锁、跨章节依赖**图中渲染占位节点**、**不做缩放平移**（用户取消）。
### AI 依赖生成（核心，防单一直线）
- `buildAiSummary()`（taskline.js）增强：(1) 主线每个章节和每条素质线追加**关键任务锚点**行「关键任务锚点：[ID:xxx]标题、…」（仅 kind=main，每线限 6 个防 prompt 膨胀），供 AI 引用为跨章节 deps；(2) 末尾新增 **📐 DAG 设计指导**段：任务线是多线交织 DAG 非单一直线链、deps 可跨章节引用锚点、主线关键任务作锚点/支线挂靠交叉、禁止 A→B→C→D 单链、deps 须无环、跨章节引用前用 quest_get 确认任务存在。
- `js/ai-tools.js`：`quest_create`/`quest_update` 的 description 加「⚠️ 依赖设计（DAG）」警示 + params.deps 描述改为「可引用任意章节任务ID（跨章节依赖），用摘要中 [ID:xxx] 锚点」。
- **deps 有效性校验**：`quest_create` 执行后检查 deps 中不存在的任务 ID → 返回 `⚠️ 警告：[ids] 不是有效的任务 ID，该任务将保持锁定，请用 quest_get 确认后 quest_update 修正`（不阻断创建，草稿可后续修正）；`quest_update` 设 deps 时同样校验并提示。AI 引用悬空 ID 会让任务永远 locked——这是「AI 处理不好依赖」的直接表现之一。
